# 智能问答助手

基于知识库的 RAG 语义检索问答服务，带配套前端界面。

## 它做什么

用户在页面上提问 → 系统从知识库中检索最相关的条目 → 交给大模型生成回答。

生成的回答**严格依据检索到的材料**，材料不足时明确说「无法回答」而不是编造。
界面上会同时展示回答和它的依据（可展开查看命中了哪些知识条目），
方便核对是检索错了还是模型答偏了。

## 架构

```
提问 → 向量化
        ├─ 查「问题索引」→ 候选 A（问法匹配，含每条知识的所有问法变体）
        └─ 查「答案索引」→ 候选 B（内容匹配）
      按知识条目合并去重 → rerank 精排 → 取 top_k → 大模型生成 → 回答 + 依据
```

整条链路是**串行**的，各阶段耗时（实测，40 条知识 / 164 行问题向量）：

| 阶段 | 耗时 |
|---|---|
| embedding | 约 0.6s |
| 检索 + rerank | 约 1.0s |
| 大模型生成 | 约 1.4s |
| **合计** | **约 3~4s** |

命中为空时会跳过生成（不调模型），响应降到 1s 以内。
多轮追问会多一次「查询改写」调用，约多 0.9s。

## 问法变体（aliases）与索引清单

一条知识可以有多个问法变体。**每个变体必须单独成为一个向量**，不能拼成一个字符串：

```json
{"id": "KB001",
 "question": "每学期什么时候选课？在哪个网址选？",
 "aliases": ["什么时候选课", "选课网址是什么", "选课系统在哪进"],
 "answer": "...", "source": "...", "url": "...", "updated": "..."}
```

`question` 与 3 个 alias 会产出 **4 个向量**，都指向 `KB001`。这样做的代价是
**索引行数不再等于知识条数**（40 条知识 → 164 行向量），行号不能当条目下标用。

所以索引旁边必须有一份清单：

```
index/
├── question.index     164 行
├── answer.index        40 行
└── manifest.json      每行属于哪个知识 id + 模型名 + 内容指纹
```

启动时校验清单与当前配置/知识库是否一致（模型、条数、行数、内容指纹），
**不一致就拒绝启动**，而不是带着错位的索引静默返回错误答案。
`STRICT_INDEX_CHECK=false` 可临时降级为告警，但检索结果不可信。

**为什么不能拼接变体**：向量化把整段文本压成一个点。多个语义分散的问法拼在一起
会得到一个「平均值」，跟任何一个具体问法都不像。实测 5 个语义不同的变体
（空调 / 洗澡 / 几人间）拼接后 Top-1 为 **0/5**，比不加变体还差。

## 检索效果（40 条知识 / 164 条用例）

| 类型 | 条数 | Top-1 | Recall@5 | MRR |
|---|---|---|---|---|
| 直问 | 40 | 100% | 100% | 1.000 |
| 别名 | 124 | 93.5% | 100% | 0.968 |
| **合计** | **164** | **95.1%** | **100%** | **0.976** |
| 无关问题拒答 | 10 | 80%（2 条误报） | — | — |

单次检索平均 1.6s（含 rerank），P95 2.0s。

> **这个数字的口径必须说清楚**：别名层的查询取自数据里已有的 alias，
> 而这些 alias 同时也是索引内容，所以指标偏乐观 —— 真实用户会用我们
> 没写进 alias 的说法。更严格的留出法测试见 `tests/eval_aliases.py`，
> 那里 Top-1 只有 79.5%（基线）/ 75.0%（多变体），说明**未覆盖问法仍有明显差距**。
> 两组数字不能混用：前者说明「已覆盖问法能否命中」，后者才是泛化能力。

多轮追问会多一次「查询改写」调用，约多 0.9s。

## 多轮对话

前端会自动带上 `session_id`，追问可以省略主语：

```
用户：宿舍条件怎么样
用户：它有空调吗          ← 系统理解为「宿舍有空调吗」后检索
```

**关键在查询改写。** 检索层只看到「它有空调吗」，离开上文和任何知识都匹配不上
（实测命中 0 条）。所以检索前先用模型结合历史把追问补全成独立问题：

| 追问 | 改写为 | 命中 |
|---|---|---|
| 它有空调吗 | 宿舍有空调吗 | 0 → 2 |
| 它在哪里 | 西安电子科技大学在哪里 | 0 → 5 |
| 那食堂呢 | 食堂怎么样 | 0 → 1 |
| 宿舍条件怎么样（已完整） | 原样返回 | 不变 |

改写有两条硬约束：**已经是完整问题时原样返回**（避免把「学校在哪」改坏），
**只补全指代、不引入上文没有的信息**。界面上会显示「已结合上文理解为：…」，
改写错了用户能立刻发现。

会话使用 `keep_history` 控制：

```bash
# 单轮（默认）：不读也不写历史
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" -d '{"query":"学校在哪"}'

# 多轮：首次不传 session_id，服务端新建并在响应里返回
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query":"宿舍条件怎么样","keep_history":true}'

# 追问：带上拿到的 session_id
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query":"它有空调吗","keep_history":true,"session_id":"<上一步返回的>"}'
```

> **会话当前存在内存里**，有两个边界：`uvicorn --workers 2` 时多个进程各存一份，
> 同一会话落到不同 worker 会丢历史；进程重启历史即丢。
> 单进程开发/小规模部署够用，要多 worker 需换 Redis。

**为什么问题和答案分开建索引**

早期做法是把 `question + answer` 拼成一条文本去向量化，有两个问题：

1. **语义稀释**：答案文字会冲淡问题向量的语义。本知识库条目大多以
   「西安电子科技大学」开头，区分度本来就低，再混入答案就更挤在一起。
2. **答案向量被浪费**：用户问法和知识库问法经常对不上（用户问「风景美不美」，
   知识库里写的是「校园环境怎么样」），但答案正文里可能有相关信息。
   把答案单独建索引，这条就能被捞回来。

**为什么需要 rerank**

向量检索是「双塔」结构：问题和文档各自独立编码，编码时互相看不见，
会丢掉细粒度交互信息。rerank 是 cross-encoder，把 query 和候选文档
拼在一起打分，排序远比向量点积准。它的分数还能用来判断「该不该回答」。

**为什么关掉大模型的深度思考**

`deepseek-v4.1-flash` 默认开启思考模式，会先输出一大段思维链。实测：

```
默认思考                约 2.2s，产生 63 个 reasoning token
enable_thinking=false   约 1.6s，0 个 reasoning token
```

RAG 的材料和问题都摆在明面上，不需要多步推理；思维链还按输出 token 计费，
所以默认关闭（`LLM_DISABLE_THINKING=true`）。

## 目录结构

```
├── main.py                 启动入口（uvicorn main:app）
├── build_index.py          建索引：问题、答案各建一个
├── requirements.txt        运行依赖
├── .env.example            配置模板（复制成 .env 后填值）
│
├── api/
│   └── rag_service.py      HTTP 层：/get_answer /ask /health /ui-config + 静态托管
├── service/                业务层（不依赖 web 框架，可单独测试）
│   ├── config.py           配置读取与校验（Settings 为不可变快照）
│   ├── embedding.py        embedding 客户端（自动分批，接口单次上限 10 条）
│   ├── vector_index.py     FAISS 索引封装（内积 + L2 归一化 = 余弦相似度）
│   ├── rerank.py           rerank 抽象 + Noop 实现 + qwen3-rerank 实现
│   ├── llm.py              大模型生成与查询改写（提示词约束 + Noop 实现）
│   ├── session.py          多轮会话存储（内存 + TTL + 轮数上限）
│   └── rag.py              双路召回、合并去重、精排、改写、生成
├── frontend/               零构建纯静态前端（原生 HTML/CSS/JS）
├── db/
│   └── data.json           知识库正文（人工维护）
├── index/                  向量索引（由 build_index.py 生成，不入库）
└── tests/                  验证与评测脚本
```

## 快速开始

```bash
# 1. 安装依赖
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements.txt

# 2. 配置
copy .env.example .env      # 然后填入 DASHSCOPE_API_KEY

# 3. 验证 Key 是否可用
venv\Scripts\python.exe tests\check_api.py

# 4. 建索引（改了知识库后都要重跑）
venv\Scripts\python.exe build_index.py

# 5. 启动
venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

打开 <http://127.0.0.1:8000> 即为界面。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 重定向到界面 `/ui/` |
| GET | `/health` | 服务与索引状态（**索引数不等于知识数时 `ready=false`**） |
| GET | `/ui-config` | 前端启动配置（标题、查询地图地址） |
| POST | `/ask` | **问答主入口**：检索 + 生成回答 + 依据 |
| POST | `/get_answer` | 只做检索，返回拼好的上下文字符串（不调模型） |
| GET | `/docs` | 自动生成的 API 文档 |

`/ask` 的 `generate` 参数可覆盖默认行为：

```bash
# 默认：跟随 LLM_ENABLED（开启则生成回答）
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query":"学校在哪"}'

# 只检索、不调模型（调试检索效果时用，不产生生成费用）
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query":"学校在哪","generate":false}'
```

返回结构：

```json
{
  "answer": "学校位于陕西省西安市……",   // 生成的回答
  "generated": true,                    // 是否由大模型生成
  "generation_error": "",               // 生成失败时的原因（此时 answer 退回材料原文）
  "matched": true,                      // 是否检索到内容
  "hit_count": 3,
  "hits": [ { "question": "...", "answer": "...", "score": 0.61, "rerank_score": 0.61 } ]
}
```

## 测试与评测脚本

均在项目根目录执行：

| 脚本 | 作用 | 是否消耗 API 额度 |
|---|---|---|
| `tests/check_api.py` | 验证 API Key 与接口连通性 | 极少（一条请求） |
| `tests/_selftest.py` | 离线全链路自检（假 embedding，含行映射/按条目去重/降级） | 不消耗 |
| `tests/test_dedupe.py` | 验证按知识条目去重、不按答案文本误合并 | 不消耗 |
| `tests/check_ui_contract.py` | 检查 HTML/JS/CSS 引用是否对得上 | 不消耗 |
| `tests/eval_retrieval.py` | 检索效果评测（自动生成用例，分层报 Top-1/Recall/拒答） | 消耗 |
| `tests/eval_aliases.py` | 留出法验证 aliases 与拼接方案的真实差异 | 消耗 |
| `tests/check_llm.py` | 验证大模型生成链路与拒答行为（需先启动服务） | 消耗 |
| `tests/check_multiturn.py` | 验证多轮指代消解、会话隔离、重置（需先启动服务） | 消耗 |
| `tests/check_ui.py` | 前端与接口联调（需先启动服务） | 消耗 |

`eval_retrieval.py` 的用例**从数据自动生成**，所以知识库怎么改都能直接跑，
不会再出现「用例引用了已删除的问法」这种静默失效。

## 调参须知（重要）

**阈值是按实测分数分布定的，不是通用值。** 换 embedding 模型或大改知识库后，
分数的绝对尺度会变（实测 `text-embedding-v3` 与 `v4` 的尺度就不一样，
互相照搬会全错），必须重新扫：

```
分别测「有效查询的最低分」和「无关查询的最高分」，阈值取两者之间。
若两者重叠，说明该路无法用单一阈值干净分离，只能取舍。
```

`.env` 里有三个独立阈值，它们**不同源，不能混用**：

- `SCORE_THRESHOLD` —— 问题索引的向量相似度
- `ANSWER_SCORE_THRESHOLD` —— 答案索引的向量相似度
- `RERANK_SCORE_THRESHOLD` —— rerank 分数（仅在开启 rerank 时生效，
  且它才是「该不该回答」的实际门槛）

还有一个**容量**参数需要注意：`RECALL_OVERFETCH`。有问法变体时同一知识占多个
索引行，实测取 top_5 平均只拿到 3.0 个不同条目 —— 不超取的话 40% 的候选位会被
同一条知识的变体浪费掉。

跑 `tests/eval_retrieval.py` 可以看到当前配置下的分层指标与拒答率。

## 知识库格式

`db/data.json` 支持两种格式，程序自动识别（`[` 开头按 JSON 数组，否则按 JSONL）：

**JSONL（推荐，一行一条，便于 diff 与追加）**

```jsonl
{"id": "KB001", "category": "选课", "question": "每学期什么时候选课？", "aliases": ["什么时候选课", "选课网址是什么"], "answer": "……", "source": "……", "url": "……", "updated": "2026-10-31"}
{"id": "KB002", "category": "选课", "question": "选课分几轮？", "aliases": ["预选是什么意思"], "answer": "……", "source": "……", "url": "……", "updated": "2026-10-31"}
```

**JSON 数组（旧格式，仍兼容）**

```json
[
  { "id": "d1", "question": "学校在哪", "answer": "西安电子科技大学位于……" }
]
```

字段要求：

| 字段 | 必需 | 说明 |
|---|---|---|
| `id` | **是** | 唯一标识。有问法变体后行号不等于条目下标，必须靠 id 映射 |
| `question` | 是 | 标准问法 |
| `aliases` | 否 | 问法变体数组，每个变体独立向量化 |
| `answer` | 是 | 答案正文 |
| `category` / `source` / `url` / `updated` | 否 | 元数据，不参与向量化，改动不会导致索引过期 |

**`id` 缺失或重复会直接报错**，不会用下标兜底 —— 用下标兜底会得到「看起来正常
但答案是错的」结果，比启动失败更糟。

改完知识库后必须重建索引（`build_index.py`），否则 manifest 的指纹校验会发现
内容已过期并拒绝启动。

## 已知限制

- **端到端延迟约 3~4 秒**：embedding、rerank、生成是串行三次网络请求。
  多轮追问再加一次改写调用（约 +0.9s）。
  「检索 + rerank」约 1.0s。想压延迟可以调小 `RECALL_K` 与 `RECALL_OVERFETCH`，
  但要重新跑评测确认召回没掉。
- **别名层指标偏乐观**：`eval_retrieval.py` 用已有 alias 当查询，而这些 alias
  同时也在索引里。留出法（`eval_aliases.py`）显示 Top-1 只有 79.5%，
  说明**未覆盖问法仍有明显差距**，不要拿 95.1% 当泛化能力。
- **同分类条目互相抢位**：8 条同类知识的向量高度邻近，别名会让候选池更拥挤。
  实测 8 条别名 Top-1 失败全部是「同分类相邻条目排到了第一」，
  靠 rerank 部分修正（也带来 2 条误报）。
- **rerank 是双刃剑**：它把拒答率从 30% 提到 80%，但让别名 Top-1 从 100% 降到
  93.5%。这是当前配置的取舍，换数据后要重新权衡 `RERANK_SCORE_THRESHOLD`。
- **多轮会话存在内存里**：`uvicorn --workers N`（N>1）时同一会话落到不同
  worker 会丢历史；重启即丢。
- 大模型可能仍会轻微改写措辞（如把「西安电子科技大学」简称成「学校」），
  提示词已要求只用材料内容，但不能保证 100% 逐字忠实。
- 查询改写依赖模型判断，偶有把完整问题误改的可能；界面上会显示改写了什么，
  便于用户发现。
- 前端未做鉴权，`/ask` 等接口对外暴露，**不要直接部署到公网**。
